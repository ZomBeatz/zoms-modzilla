# Zom's Nexus

Zom's Nexus is a ZomBeatz Media tool: a Nexus Mods manager for Linux (downloads, collections, profiles that put mods into games, conflict checks). Tauri 2 (Rust) with a React + TypeScript + Vite page, built like Zom's MRP (`../Zoms_MRP`).

- **Design and wording:** follow the ZomBeatz design system: https://github.com/ZomBeatz/zombeatz-docs/blob/main/design/DESIGN.md (locally `../zombeatz-docs/design/`). `src/tokens.css` is a copy of its `tokens.css`; build styles from the `--zb-*` variables.
- **The download queue** (`src-tauri/src/queue.rs`) is the heart of it. Sequential = 1 slot, concurrent = `max_concurrent` slots (1 to 8), auto = concurrent for Premium and 1 for free accounts; `Settings::slots(premium)` decides, and `Queue::schedule` hands out slots in list order whenever it's poked. Starting, downloading and storing (moving into the library and unpacking) all hold a slot, so sequential really is one file at a time from start to finish. Downloads resume with HTTP Range from `<library>/.incoming/<id>.part`. A job's nxm key never reaches the page (`Job::public`).
- **Nexus Mods rules:** free accounts may only download a file after clicking **Mod manager download** on the website (the nxm link carries a key and expiry); only Premium accounts get links straight from the API. Never work around that. Every API call sends `Application-Name`/`Application-Version` and counts against the person's rate limit, so don't add calls in loops.
- **Library layout** (`library.rs`): `<library>/<game>/<mod id> - <name>/` with `nexus.json`. Commands only ever touch folders found through `library::find`, and every name from Nexus Mods goes through `safe_name`. Unpacking refuses paths that leave the folder.
- **nxm links:** `nxm_register` writes `~/.local/share/applications/com.zombeatz.zoms-nexus-nxm.desktop` and runs `xdg-mime`; the deb/rpm desktop file (`src-tauri/desktop.template`) also lists the scheme. A second start hands its link to the running app (single-instance plugin).
- **Commands:** a new Rust command goes in `generate_handler!` (lib.rs), `build.rs` and `capabilities/default.json`, and in `src/api.ts` and `src/demo.ts`.
- **The demo** (`src/demo.ts`) runs the page in a plain browser with made-up mods and pretend downloads that follow the same slot rules. Use it for screenshots; never real mod or account data.
- Run `npm test`, `npm run build` and `cargo test --manifest-path src-tauri/Cargo.toml` before calling something done. The queue tests start a small stand-in for Nexus Mods on 127.0.0.1.
- **Putting mods into games** (`deploy.rs`): hard links (copies across drives) into `<game>/<mod folder>`, a manifest per game in the data folder, game files moved to `<game>/.zoms-nexus-backup` and put back by `clear`. Never delete a game file that isn't in the manifest. `entries()` decides where each file goes and is shared with the conflict check (`check.rs`, which also reads plugin masters from TES4 headers). Profiles and mod packs are in `profiles.rs`; a pack lists Nexus Mods numbers only, never mod files (redistributing them isn't allowed).
- **Collections** (`collections.rs`) and nothing else use the v2 GraphQL API (`Nexus::graphql`); keep its query small and its parsing tolerant. **Art** (`art.rs`) comes from Steam's local cache, then Steam's CDN, then Nexus Mods' game tile, and is cached in the app cache folder.
- **Thunderstore** (`thunderstore.rs`): games, loaders and install rules come from Thunderstore's public ecosystem file (cached a day); a community's mod list from its CDN (cached an hour). Only BepInEx games install. Mods get numbers at `thunderstore::IDS` (above `LOCAL_IDS`), so they're never looked up on Nexus Mods or put in Nexus packs. r2modman profiles/codes and MO2 (`mo2.rs`) import into profiles; tModLoader (`tml.rs`) is managed through its own `enabled.json` and mod packs.
- **Steam's files are only read**, with one exception the person asks for: **Add to Steam** (`steamshortcut.rs`) writes `shortcuts.vdf` only while Steam is closed, keeps every other entry byte for byte, and saves a backup first. Launch options and settings are never written.
- **Steam Deck**: `deck.ts` (Deck mode, size), `pad.ts` (D-pad focus moves, buttons), `gamepad.rs` (controllers read natively via gilrs, sent as `pad` events). Controller input is ignored while a game is starting or running, and when the window isn't focused.
- **Troubleshooting**: `runs.rs` (each Play's mods and run time; quick exits vs. the last good run), `loaders.rs` (loaders recognised by their files, their logs read), `modsettings.rs` (settings files kept per profile, copied never linked). `deploy::apply` leaves files that are already right in place.
- **AI help** (`ai.rs`) is optional and off by default: Claude by its Messages API, anything else by the OpenAI-style chat API. The key lives in `ai-key` (0600), never in settings or the page. `ai_context` builds what's sent, scrubbed (home folder, user names, keys), and the person sees it before Send.
- **LOOT** (`loot.rs`): plugin order from LOOT's masterlists on GitHub (cached a day), kept per profile in `<data>/plugin-order/<profile>.json`, apart from the mod order; `deploy::apply` writes plugins.txt in mod order with that order on top. **Baldur's Gate 3** (`bg3.rs`): .pak mods into the prefix's Mods folder (tracked in `deployed/baldursgate3-paks.json`) and `modsettings.lsx`; other tools' entries and files are kept. **Save snapshots** (`snapshots.rs`): zips in `<data>/save-snapshots/<game>/`; restoring moves the current saves aside, never deletes.
- **Flatpak** (`host.rs`, `packaging/flatpak/`): inside the sandbox, processes, signals and launches go through `flatpak-spawn --host`; the update check (`release.rs`, GitHub `ZomBeatz/zoms-nexus`) is off there.
